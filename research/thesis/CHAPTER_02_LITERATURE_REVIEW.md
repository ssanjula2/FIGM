# Chapter 2: Literature Review

## 2.1 Chapter Overview

This chapter reviews the literature underpinning the research problem set out in Chapter 1. It maps the domains this research draws on, establishes the foundational concepts of Single Page Application (SPA) architecture, rendering, state management, performance, and accessibility, critically examines the existing tools that address parts of this problem space, and analyses the algorithmic, design, and workflow foundations relevant to a framework-agnostic guideline model and its automated validation tool. The chapter closes by synthesising this evidence into the specific research gap this dissertation addresses. Consistent with Chapter 1, this chapter reports literature and existing-tool evidence only; the Framework-Agnostic Guideline Model (FIGM)'s own measured results are reserved for Chapters 5 and 6.

## 2.3 Domain Overview

A Single Page Application loads a single HTML document once and thereafter updates its content asynchronously in the browser, rather than requesting a new document from the server for every user action — the defining departure from the earlier Multi-Page Application (MPA) model [12], [13]. This shift moved a substantial share of an application's logic — rendering, routing, and state — from the server into the browser, and gave rise to the component-based architecture this dissertation's primary frameworks, React [17], Next.js [18], and Angular [19], each implement in their own way; Vue.js [20] implements the same general architecture as the additional framework this research's validation tool also supports.

Two architectural decisions recur across all of these frameworks and are directly relevant to this dissertation's research questions. The first is **rendering strategy**: whether a page's initial HTML is produced by executing component code in the browser (client-side rendering, CSR) or on the server before the response is sent (server-side rendering, SSR), with hydration then attaching client-side interactivity to server-rendered markup, or pre-rendering producing static HTML ahead of any request. A recent controlled comparison of CSR and SSR reports measurable differences in Core Web Vitals — including First Contentful Paint (FCP) — between the two strategies under the conditions it tested [21], which is direct evidence that rendering strategy is not a cosmetic implementation detail but a variable with observable performance consequences — precisely the relationship RQ1 investigates for this dissertation's own controlled fixture (Chapter 3). The second is **state management**: whether data is held locally within a single component or in a shared, application-wide store accessible across components, a distinction a recent review of state-management approaches across web and mobile platforms treats as a first-class architectural concern in its own right, independent of which specific library or framework implements it [22].

Performance in this context is most concretely expressed through metrics such as First Contentful Paint (FCP) and Time to Interactive (TTI) — the two metrics RQ1 investigates — alongside broader concerns such as unnecessary re-rendering and JavaScript bundle size, all of which ISO/IEC 25010:2011 frames as instances of the technology-independent *Performance Efficiency* quality characteristic rather than as framework-specific concerns [1]. Accessibility, in the SPA context specifically, introduces risks that a traditional server-rendered page does not share to the same degree: content that updates without a full page reload can leave assistive technology unaware that anything changed unless the update is explicitly announced, keyboard and focus behaviour must be maintained manually across client-side navigation, and semantic structure must be preserved as components mount and unmount dynamically. The Web Content Accessibility Guidelines (WCAG) 2.2 state the applicable success criteria in technology-neutral terms [2], and research on automated accessibility evaluation has treated exactly this class of dynamic-content risk as a motivating problem for tooling that can navigate and test a page's interactive states rather than only its initial markup [14].

Static program analysis — inspecting source code by parsing it into a structured representation and analysing that representation, rather than executing the program — is the technical foundation this dissertation's own validation tool is built on; §2.5.1 develops the algorithmic detail this domain overview only introduces here.

## 2.4 Existing Systems / Frameworks / Designs

Four categories of existing tool address parts of the problem space Chapter 1 describes, and each is examined here for what it does, on what kind of evidence, and where its coverage stops relative to this dissertation's research gap — not merely listed by name.

**Google Lighthouse** [23] audits a running page in the browser and reports Core Web Vitals and related performance metrics, including First Contentful Paint and (in earlier releases) Time to Interactive — the same class of metric RQ1 investigates. Lighthouse's analysis is inherently a **runtime** measurement: it observes the consequence of an architectural decision (a slow paint, a long main-thread task) after the application has been built and executed, without inspecting the source code that produced that consequence. This is a genuine strength for the question Lighthouse is designed to answer — it measures what a user's browser actually experiences — but it is also the tool's structural limitation relative to this dissertation's problem: a Lighthouse report cannot, by construction, point back to the specific component, hook, or rendering decision responsible for a given result, because it never inspects that source code at all.

**ESLint** [24], together with its framework-specific plugin ecosystem (`eslint-plugin-react` for React, `angular-eslint` for Angular, and comparable plugins for other frameworks), performs genuine **static**, source-level analysis — parsing code into an Abstract Syntax Tree and matching rules against it, the same general technique this dissertation's own tool depends on (§2.5.1). Its structural limitation is different from Lighthouse's: coverage is organised **per framework**, through independently maintained plugin packages, with no shared, formal statement of a guideline that a reader could confirm is the identical rule enforced consistently across React, Angular, and Vue — precisely the fragmentation problem Chapter 1 (§1.3.2, point 1) identifies. ESLint's rule engine is also general-purpose; performance-risk and accessibility-specific reasoning is not native to the core tool and depends on which plugins a project happens to have configured.

**SonarQube** [25] performs static, source-level analysis for general software-quality concerns — code smells, duplication, maintainability metrics, and a limited set of security and reliability rules — across many languages, not specifically SPA frameworks. Its architectural awareness is at the level of general code-quality heuristics rather than SPA-specific concerns such as rendering strategy or component re-render cost, and its accessibility coverage is effectively absent; it is, in the terms of this dissertation's problem statement, a framework-agnostic tool in the trivial sense of being language-general, but not in the sense of formally modelling SPA-specific architectural or accessibility guidance.

**axe DevTools** [26] performs runtime, DOM-based accessibility auditing, checking a rendered page's accessibility tree against a large, well-regarded rule set derived from WCAG and related standards. Empirical research on the design of automated accessibility-evaluation tools more broadly has found that such tools can differ substantially in what they check and how transparently that scope is communicated to a user, which is a direct caution against treating any single automated accessibility audit — including axe's — as a complete measure of WCAG conformance [15]. Like Lighthouse, axe's analysis happens after the page has been rendered in a browser; it shares Lighthouse's structural limitation of not being able to trace a finding back to the source-code pattern responsible for it, even though its accessibility coverage is otherwise strong within its runtime scope.

## 2.5 Technological Analysis

### 2.5.1 Algorithmic Analysis

Static analysis begins with lexical and syntactic parsing: source text is tokenised and then structured into an Abstract Syntax Tree (AST), a hierarchical representation of the program's syntactic structure — the standard architecture described in the classical compiler-construction literature [4]. Analysis is then performed *over* this tree rather than over raw text, which is what distinguishes AST-based detection from a purely textual pattern match (a regular expression over source text): the same syntactic shape can be located reliably regardless of incidental formatting, comment placement, or variable naming, because the AST already discards that irrelevant variation.

A more fundamental distinction, developed in the static-analysis literature, is between *syntactic* pattern matching — recognising that a particular shape of code appears — and *semantic*, data-flow or abstract-interpretation-based analysis, which answers a stronger question: not "does this shape appear" but "what values can flow to this program point under any possible execution" [5]. Abstract interpretation, in its original formulation, defines the conditions under which a static analysis can be *sound* — free of false negatives by construction, via a computable approximation of a program's concrete semantics [6]. This distinction matters directly to how a framework-agnostic guideline model should be scoped: a rule that only needs to recognise a syntactic shape (for example, an inline object literal re-created inside a loop body) can be implemented as an AST pattern match with modest engineering cost, while a rule that requires knowing what a variable's *value* actually is at a given point — full data-flow or points-to analysis — is a substantially harder problem, and a tool that implements only the former should not claim the soundness guarantees the latter, formally defined by abstract interpretation, would provide. A framework-agnostic guideline model that aims to be practically deployable across multiple frontend frameworks must therefore make an explicit, disclosed choice about where on this spectrum each of its rules sits, rather than leaving that choice implicit.

Framework-specific syntax handling is the second major algorithmic concern this literature raises for a cross-framework tool. React and Next.js source is standard JavaScript/TypeScript with embedded JSX, parseable by a general-purpose ECMAScript/TypeScript parser; Angular components combine TypeScript class bodies with a separate template syntax that requires its own parser; Vue's single-file components combine template, script, and style blocks in one file format requiring a dedicated compiler. A tool that wants to express one guideline once and check it against all of these must therefore separate two concerns that a single-framework linter does not need to separate: a **framework-specific parsing layer**, responsible only for producing a structured representation of each framework's own syntax, and a **framework-agnostic rule layer**, responsible for the semantic question the guideline actually asks, expressed against a normalised view of that structure rather than against any one framework's native AST shape. This separation — parse framework-specifically, reason framework-agnostically — is the direct algorithmic consequence of wanting one guideline definition to apply across syntactically different frameworks, and is the reason a framework-agnostic tool cannot simply reuse a single framework's own linter architecture unmodified.

Source normalisation of this kind, and rule-based tree traversal generally, carries a further, well-established trade-off: broadening a pattern to catch more true violations (reducing false negatives) tends to also catch more code that resembles the pattern without actually being a violation (increasing false positives), and narrowing a pattern to avoid false positives tends to miss genuine violations expressed slightly differently (increasing false negatives) [5]. No purely syntactic detector can eliminate both simultaneously without approaching the harder, semantic analysis problem described above; a framework-agnostic guideline model that is transparent about this trade-off, rule by rule, is making a more defensible claim than one that presents its detection as complete. This is the algorithmic foundation this dissertation's own design decisions (Chapter 3) and implementation (Chapter 4) are built against, without pre-empting here what those chapters report about how any specific rule resolves the trade-off.

### 2.5.2 Design Analysis

Where §2.5.1 addresses *how* a piece of source code can be inspected, this section addresses *how a guideline itself should be modelled* so that one definition can be projected consistently onto several structurally different frameworks. The central design problem is separating a guideline's **semantic concern** — the underlying architectural or accessibility principle a guideline expresses — from its **framework-specific syntactic realisation**. "Avoid re-creating an object on every render" is a semantic concern; the specific code shape that realises a violation of it looks different in a React function component, a Vue single-file component, and an Angular component class. A guideline model that only encodes the syntactic realisation cannot be reused across frameworks without being rewritten from scratch for each one; a guideline model that encodes only the semantic concern, with no defined path to an executable check, remains a prose recommendation rather than something a tool can enforce. Standards such as ISO/IEC 25010 [1] and WCAG 2.2 [2] provide exactly the semantic vocabulary this modelling problem needs at the top level — categories such as *Performance Efficiency* or a specific accessibility success criterion — but neither standard itself specifies the executable, AST-level check that would determine compliance in a specific framework's source code; that translation is a design problem the standards leave open, not one they solve.

Established object-oriented design vocabulary offers a general pattern for structuring exactly this kind of variability: separating a stable interface (the semantic concern, expressed once) from interchangeable, framework-specific implementations (the syntactic realisation, expressed per framework) is the same shape of problem the Strategy, Factory, and Adapter patterns are conventionally used to address [9] — selecting between interchangeable behaviours behind a common interface, constructing the correct concrete implementation without the caller needing to know which one, and presenting a uniform interface over structurally different underlying representations, respectively. These patterns are cited here for their general relevance to the framework-abstraction design problem this literature raises, not as a description of any specific class in this dissertation's own implementation, which is reserved for Chapter 4. A parser's own type-system design is a related but narrower concern: a structurally-typed, error-tolerant parser — of the kind TypeScript's own compiler implements [7] — is valuable specifically because production source code is not always well-formed at the moment a validation tool inspects it, and a parser that fails outright on malformed input is unusable in that setting, whereas one designed for tolerant, structural parsing can continue to produce a usable representation.

A critical distinction this design analysis must maintain — and one this dissertation treats as a first-order methodological commitment rather than a footnote — is between a **conceptual guideline** and an **executable static rule**. Not every principle a standard or a body of architectural best practice states is statically detectable at all: WCAG 2.2's success criteria include some conditions a static analysis of source code can check directly (for example, whether an interactive element is reachable by keyboard in principle), some it can check only partially or heuristically (for example, whether an ARIA label's *content* is meaningful, as opposed to merely present), and some it cannot check at all without a genuine understanding of visual layout or user intent that static source inspection does not have access to. A framework-agnostic guideline model that does not make this distinction explicit — that implies every guideline it names is fully, automatically enforced — overstates what static analysis alone can establish; RQ2's own wording ("in compliance with WCAG 2.2 guidelines," Chapter 1, §1.4) states the destination as a standards target, while this dissertation's own scope statement (Chapter 1, §1.10) is deliberately narrower: a *statically detectable subset* of WCAG 2.2-related concerns, never a claim of full conformance.

### 2.5.3 Workflow Analysis

The two categories of tool examined in §2.4 correspond to two structurally different workflows, and comparing them directly clarifies where a framework-agnostic static validation tool is positioned relative to existing practice, rather than in competition with it.

A **runtime audit** workflow — the one Lighthouse and axe DevTools both implement — proceeds: build and run the application → load it in a real or emulated browser → measure or inspect the resulting page → report an observed symptom (a slow paint metric, a failed accessibility check against the rendered DOM). Its strength is fidelity: it measures what actually happens when the application executes, which is the only way to obtain a genuine FCP or TTI value (the reason this dissertation's own RQ1 investigation, Chapter 3, uses exactly this workflow, via Lighthouse, rather than attempting to estimate FCP/TTI statically). Its structural limitation is temporal and diagnostic: the application must already be built, and typically deployed or run in a realistic environment, before this workflow can produce any result at all, and the result it produces is a measurement of the *consequence* of a source-code decision, not a pointer to the decision itself.

A **static validation** workflow — the one this dissertation's own tool implements, and the one ESLint and SonarQube also implement in narrower form — proceeds: source code → framework-specific parsing into a structured representation → rule-based analysis over that representation → a source-level finding, tied to a specific file and location → feedback available before the application is ever built or deployed. Its strength is exactly what the runtime workflow lacks: because analysis operates directly on source code, a finding can be traced to the specific architectural pattern responsible for it, and feedback is available at the point in the development process — before a commit, before a build — where correcting it is cheapest. Its structural limitation is equally direct: it can identify a *risk pattern* associated with a class of defect, but, absent full execution, it cannot measure the *actual* runtime consequence of that pattern in a specific deployment — which is precisely why this dissertation is careful throughout (Chapter 1, §1.9's boundary statement) never to present a static finding as if it were a measured FCP or TTI value.

These two workflows are complementary, not competing, descriptions of the same underlying problem viewed from different points in the development lifecycle, and the general engineering principle of designing a long-running analysis process to execute asynchronously rather than blocking other work — well established in concurrent-programming practice for exactly this kind of workload [8] — applies to a static validation workflow specifically because a tool intended to run automatically, potentially on every commit, must not stall the rest of a development pipeline while it works. A framework-agnostic guideline model is therefore best understood as a way to strengthen the pre-deployment half of this picture — giving a development team the source-level, architecturally-actionable feedback the runtime workflow structurally cannot provide — while leaving the runtime workflow's own, distinct strength (measuring what a real browser actually experiences) to the tools already built for exactly that purpose.

## 2.6 Reflection / Research Gap

Taken together, this literature review supports three observations this dissertation relies on directly. First, SPA architecture, rendering strategy, and state management are not incidental implementation choices but variables with demonstrated, measurable consequences for performance [21] and for state-management design [22] specifically — which is why Chapter 1's RQ1 treats their influence on FCP and TTI as an empirical question worth investigating under controlled conditions, rather than assuming the answer from general principle. Second, the existing tool landscape (§2.4) provides strong coverage of individual dimensions of this problem — runtime performance auditing, runtime accessibility auditing, general-purpose static code quality — but the reviewed tools remain fragmented along exactly the lines Chapter 1 (§1.3.2) identifies: framework-coupled rule definitions with no shared formal vocabulary, and a structural split between runtime measurement (which can observe a symptom but not its source-code cause) and static analysis (which can trace to a source-code cause but not measure a runtime consequence). Third, the algorithmic and design literature reviewed in §2.5 establishes both that a framework-agnostic guideline *can* be modelled — by separating a stable semantic concern from a framework-specific syntactic realisation, in the general sense the Strategy/Factory/Adapter design vocabulary and the parse/normalise/analyse algorithmic architecture both support — and that doing so honestly requires disclosing, rule by rule, where a given check sits on the syntactic-pattern-to-full-data-flow-analysis spectrum, rather than presenting static detection as a complete or sound substitute for genuine program verification.

The reviewed literature showed limited evidence of these threads being joined. No tool examined in §2.4 combines a single, formally-specified guideline definition, projected via genuine source-code analysis onto more than one frontend framework, with coverage spanning both performance-risk architecture and a statically detectable subset of accessibility guidance. Existing approaches remain fragmented specifically along the five lines Chapter 1 (§1.3.2) states: (1) guideline enforcement organised per framework rather than around a shared formal definition; (2) framework-agnostic architectural principles that, where discussed, remain at the level of prose recommendation rather than an operationalised, checkable model; (3) a persistent split between runtime assessment and pre-deployment static validation, with the surveyed tools clustering heavily on one side or the other rather than bridging it; (4) limited connection from an observed quality symptom back to the specific source-code structure responsible for it, particularly on the runtime side of that split; and (5) performance-oriented and accessibility-oriented tooling developing largely as separate concerns rather than as two facets of one guideline model.

This is the gap this dissertation's proposed solution (Chapter 1, §1.6–§1.8) responds to directly: a framework-agnostic guideline model, expressing performance-oriented architectural guidance and a statically detectable subset of accessibility guidance within one formal definition, enforced by an automated static validation tool capable of applying that definition — via framework-specific parsing but framework-agnostic rule semantics (§2.5.1–§2.5.2) — to source code before deployment, across React, Next.js, and Angular as the primary evaluated frameworks, with Vue.js as additional implementation support. Chapter 3 now presents the methodology and formal model constructed to pursue this, and Chapter 4 details its implementation.
