## 6.1 Summary of Dissertation Contributions

Modern Single-Page Application (SPA) development across React, Next.js, and Angular suffers from fragmented, framework-specific quality assurance tooling. Prior static analysis tools (e.g. ESLint, SonarQube, Lighthouse) operate in silos, lacking a unified meta-model capable of abstracting cross-framework rendering and performance anti-patterns.

This dissertation addressed this gap by designing, implementing, and empirically evaluating the **Framework-Independent Guideline Model (FIGM) Code Inspector**. The major scientific and technical contributions of this research comprise:

1. **The 4-Layer Meta-Model and Abstract Language Primitives (ALPs)**: Formalized a framework-independent abstraction hierarchy (Domain $\rightarrow$ Concern $\rightarrow$ ALP $\rightarrow$ Rule) that maps heterogeneous JSX, Vue SFC, and Angular template constructs into canonical AST primitives (`ALP-LOOP-ALLOC`, `ALP-LAYOUT-ELEMENT`, `ALP-ASYNC-DISPOSAL`, etc.).
2. **The 50-Rule Static Detection Engine**: Developed an automated static analysis engine with 50 formal predicates covering Universal Common, Next.js App Router, React State/Rendering, Vue SFC, and Angular RxJS/DOM security guidelines with confidence scoring (0–100). **Correction (this audit pass, verified directly from `src/ast/ast-detection-engine.ts` — 50 distinct rule IDs — and cross-checked against the live `/api/research-metrics` endpoint and `docs/evidence/canonical-evaluation.json`, all three in agreement):** the engine has grown from the 25 rules described in an earlier version of this chapter to 50; this section previously understated the rule count by half. The more granular claim elsewhere in this dissertation ("23 of the 25 rules are real-AST for at least one framework") has *not* been re-verified against the current 50-rule set as part of this pass — it needs the same per-rule, per-framework re-tally this correction received, and should be treated as a known, not-yet-corrected stale figure rather than assumed still accurate at the old ratio.
3. **Multi-Stage AI Remediation Pipeline**: Integrated Gemini (model configured via `GEMINI_MODEL`, not hardcoded) with a genuine three-path architecture — a first-choice AST-deterministic fixer, a small rule-level manual-review-only set, and a sandboxed, bounded-retry Gemini path — that re-scans every generated patch and only reports a fix as verified when the original violation is confirmed gone (see `src/ai/ai-remediation-pipeline.ts`). **Correction (this audit pass, verified live):** an earlier version of this chapter, and of Chapter 4 §4.6, described an "automatic deterministic fallback engine (`RemediationEngine`)" that engages whenever Gemini fails or a patch fails validation. That is not current behavior: a live Gemini quota-exhaustion (HTTP 429) triggered during this audit's own testing returned `verified: false`, `verificationStatus: 'UNRESOLVED'`, and the original source unchanged — no fallback patch was produced by any other engine. No aggregate patch-success-rate benchmark has been run against a reproducible defect corpus — a prior claim of "100% patch generation and syntax compliance" traced to hardcoded literals with no underlying data and has been retracted rather than replaced with a different number (Section 5.3 of the empirical evaluation chapter).
4. **Empirical Evaluation**:
   - Established fixture-based ground-truth detection performance for the subset of FIGM rules with hand-labelled ground truth — see `docs/dissertation/chapter5_empirical_validation_and_benchmarks.md` (auto-regenerated from `docs/evidence/canonical-evaluation.json` on every evaluation run) for the current Precision/Recall/F1/TP/FP/FN figures and exact rule-coverage scope. Numbers are deliberately not repeated as static text in this chapter, since a hand-typed copy would drift out of sync with the live benchmark the moment either changed — a prior version of this chapter did exactly that (see git history) and reported 85.7%/94.7%/90.0% figures that had silently diverged from the real benchmark.
   - A large-scale multi-repository evaluation was not conducted; a prior claim of "30 real-world open-source repositories, 755,300 LOC" was found to be a fabricated dataset (`src/eval/repo-evaluator.ts`, since deleted) and is retracted here rather than replaced with a different number. It remains future work (Section 6.4).
   - A developer usability study (final approved target N=20; the original Research Proposal and Interim Submission 02 document a historical baseline of 80–100, reduced to 20 by a later approved research-scope decision — see `docs/research/PARTICIPANT_TARGET_DECISION.md`) has not yet collected real participant data (0/20 at time of writing); a prior claim of a completed N=12 study with a measured Cronbach's Alpha is likewise retracted as fabricated. Only the scoring pipeline's formulas have been verified against synthetic test data.

## 6.2 Research Questions Revisited

**Authoritative research-question set.** The four research questions answered in this section are sourced verbatim from the Research Proposal (Section 2.3) and confirmed unchanged in Interim Submission 02 (Section 1.4) — see Chapter 1, Section 1.4, and `docs/audit/STAGE_2_DISSERTATION_ALIGNMENT_REPORT.md` for the reconciliation record. An earlier version of this chapter answered a differently-worded RQ1–RQ4 set (framework-independent formalization / comparative tool coverage / AI-remediation validity / developer usability); that discussion was real, evidence-based work and is preserved below in Section 6.2.1 as supplementary technical evaluation — it is no longer presented as the authoritative answer to RQ1–RQ4.

- **RQ1:** *How do different SPA render and state-management strategies influence performance metrics such as First Contentful Paint (FCP) and Time to Interactive (TTI)?*
  - **Status: ANSWERED, narrow disclosed scope.** A real, browser-based FCP/TTI measurement experiment was executed 2026-09-03 under the frozen `research-freeze-v1` baseline: 4 conditions (CSR × LOCAL/GLOBAL, SSR × LOCAL/GLOBAL) over a controlled Next.js/React fixture, 1 warm-up + 10 measured runs per condition (44 real headless-Chrome/Lighthouse executions, 0 failures), real `first-contentful-paint`/`interactive` Lighthouse audits under Lighthouse's real desktop throttling preset. Observed mean FCP ranged 444.2-447.5ms and mean TTI 475.6-480.7ms across the four conditions; pooled CSR-vs-SSR and LOCAL-vs-GLOBAL differences were on the order of a few milliseconds, within each condition's own standard deviation. **No statistical significance test is computed or claimed** — this is descriptive statistics only, over one specific controlled fixture (50 simple cards, no external data fetching) and one specific environment. This result must not be generalized to Angular (no Angular RQ1 runtime fixture exists — a deliberate, disclosed scope decision, not an oversight), to more complex real applications, or read as a causal claim beyond what was directly observed. The tool's `/performance` page reports a separate static scan-duration figure, explicitly labelled as a scan-duration proxy, never conflated with this FCP/TTI experiment. Full raw and processed data: `research/rq1-experiment/raw-results/`, `research/rq1-experiment/processed-results/`; full record: `docs/audit/STAGE_8_REAL_RQ1_DATA_COLLECTION_REPORT.md`.
- **RQ2:** *What framework-agnostic architectural and accessibility patterns can be identified and standardized to improve the performance and accessibility of modern SPAs in compliance with WCAG 2.2 guidelines?*
  - **Status: Answered, on existing evidence.** 19 architecture patterns and 7 accessibility patterns have been identified, formalized, and standardized across the primary frameworks (React, Next.js, Angular) as canonical FIGM rules (`figm-spec.json`; `primaryResearchDomain()` in `src/matrix/four-layer-meta-model.ts`). The 7 accessibility rules carry an explicit, per-rule WCAG 2.2 Success Criterion mapping with a stated detectability classification (`DIRECT_STATIC_CHECK` / `PARTIAL_STATIC_CHECK` / `HEURISTIC` / `MANUAL_REVIEW_REQUIRED` / `NOT_SUPPORTED`; `WCAG_22_MAPPINGS`, `tests/wcag-mapping-integrity.test.ts`). This is explicitly a **statically detectable subset** of WCAG 2.2 — no claim of full WCAG 2.2 conformance is made anywhere in this dissertation, and none should be inferred from this answer.
- **RQ3:** *How effectively can an automated static analysis validation tool detect architectural and accessibility violations in SPA source code before application deployment?*
  - **Status: Answered, on existing evidence, with explicit caveats.** A real, compiler-derived static AST analysis pipeline exists and performs pre-deployment detection (TypeScript compiler API, `@vue/compiler-dom`, `angular-html-parser`, depending on rule and framework — Chapter 4). On the internal, self-authored controlled benchmark (`benchmarks/testbed/`), the pipeline achieves the Precision/Recall/F1 figures reported live in `docs/evidence/canonical-evaluation.json` and Chapter 5 — this benchmark is self-fulfilling by construction (Chapter 5, Section 5.1.1's circularity disclosure) and demonstrates the detectors fire correctly on their own designed cases, not independent-corpus accuracy. On a real-world corpus of 21 public repositories — 15 primary-framework repositories (React 5, Next.js 5, Angular 5) plus 6 additional implementation-support repositories (Vue 3, Generic JS/TS 3), reaching the confirmed 20–30 repository target (Chapter 1, Section 1.7) — the tool scanned 2,512 files (320,367 LOC), with 0 engine crashes and 117 files with parse errors, and produced 2,649 raw findings (393 Architecture, 1,578 Static Performance, 678 Accessibility — see `benchmarks/real-world/raw-results/_combined-summary.json` and `domain-summary.json`). These findings have **not** been independently labelled for correctness at scale (an n=18 manual spot-check exists — `benchmarks/real-world/SPOT_CHECK.md` — explicitly too small to generalize), so **no real-world precision/recall/accuracy figure is claimed**.
- **RQ4:** *To what extent does the proposed validation tool achieve acceptable accuracy levels when compared with manual expert architectural reviews using Precision, Recall, and F1-score measurements?*
  - **Status: HUMAN_DATA_PENDING. No final answer is claimed.** Independent expert architectural review is a mandatory component of this research question, not an optional validation step — the internal controlled-benchmark Precision/Recall/F1 figures cited under RQ3 above (self-fulfilling by construction, per that same section's disclosure) are explicitly **not** a substitute for it and must not be presented as answering RQ4. The independent-expert-annotation infrastructure exists and is real (`research/independent-annotation/`), but **0 real expert submissions** have been collected to date (`research/independent-annotation/results/STATUS.md`). The final Precision/Recall/F1-vs-expert-review figure this research question asks for remains pending real data collection.

## 6.3 Limitations

Despite its scientific contributions, FIGM has key technical and empirical limitations:

1. **Lightweight AST Parsing Boundaries**: **Correction (Phase 3, Dissertation Integrity — re-verified directly by re-running `RuleExecutionEngine.analyzeFile` against every fixture in `benchmarks/ground-truth.json` and reading each diagnostic's own `sourceKind` field):** this item previously said "23 of the 25 rules," predating the rule set's growth to 50 and the FIGM-ANG-03/04/08/10 (`angular-html-parser`) and FIGM-VUE-01..06 (`@vue/compiler-dom` + a real TypeScript parse of the `<script>` block) migrations. As of this correction, **all 50 canonical rules** are detected via a genuine compiler-derived AST for at least one supported framework (`src/ast/real-syntax-node-builder.ts`, `src/ast/angular-template-ast-builder.ts`, `src/ast/vue-template-ast-builder.ts`, plus the Stage-A `src/analysis/react-ast-rules.ts` module for FIGM-REACT-02). No rule is real-AST on zero frameworks. Coverage remains framework-gated, not universal: FIGM-A11Y-01, FIGM-A11Y-03, FIGM-PERF-01, FIGM-PERF-02, and FIGM-PERF-03 still fall back to text-heuristic scanning specifically on Vue SFC and/or Angular template files. See Chapter 5's live-generated throughput figures for current scan-speed measurements — a hand-typed $577\text{ LOC/sec}$ figure was previously reproduced here and had drifted from the live benchmark; it has been removed rather than replaced with a different static number.
2. **No Large-Scale or Real-World Repository Evaluation**: **Correction (Phase 3, Dissertation Integrity):** the empirical accuracy result in Chapter 5 is measured against `benchmarks/testbed` (46 fixture files spanning all 50 canonical rules as of this correction, up from the "4 files, 147 LOC" this item previously described), authored by this project rather than an independent third party -- see Chapter 5 §5.1.1's own "Circularity, stated plainly" disclosure. `benchmarks/real-world/` (real, unmodified public repositories) is separately evaluated with no hand-labelled ground truth, so no precision/recall claim is made for it. Generalization to real-world repositories at scale, and independent (non-self-authored) validation, have not been empirically tested.
3. **Semantic Validation of AI Patches**: AI patch evaluation focused on syntax validity and AST re-parsing rather than full runtime unit/integration test execution.
4. **No Human Usability Data**: The developer usability study (target N=20) has not collected real participant responses, so usability and productivity impact are not yet empirically supported.

## 6.5 Final Concluding Remarks

The FIGM Code Inspector demonstrates that unifying performance and accessibility quality assurance across modern single-page applications is both theoretically viable and practically effective. By abstracting framework-specific AST constructs into canonical Abstract Language Primitives and combining static inspection with LLM remediation, FIGM advances the state of the art in automated software quality engineering.
