# Chapter 1: Introduction

## 1.1 Background and Context

Modern Single-Page Applications (SPAs) are built on component frameworks — React, Next.js, and Angular chief among them, with Vue additionally supported by the automated validation tool described in this dissertation (see Section 1.7 for the precise primary/additional framework-scope distinction) — each with its own compilation model, template syntax, and idiomatic patterns for state, rendering, and lifecycle management. This diversity has a direct consequence for software quality assurance: a performance or accessibility defect that is conceptually identical across frameworks (for example, allocating a new object on every render, or omitting a stable list key) manifests as syntactically unrelated code in each one. A `.map()` callback in React, a `v-for` directive in a Vue template, and an `*ngFor` structural directive in an Angular template are the same defect wearing three different syntaxes.

Quality standards themselves are framework-agnostic by design. ISO/IEC 25010:2011 defines *Performance Efficiency* and other software quality characteristics as product properties, independent of implementation technology (International Organization for Standardization, 2011). The Web Content Accessibility Guidelines (WCAG) 2.2 state their success criteria as testable, technology-neutral conditions, not as framework-specific code patterns (World Wide Web Consortium, 2023). The gap this creates is an *enforcement* gap: a standard written in natural, framework-independent language has no direct, executable counterpart that can inspect a specific React component, Vue SFC, or Angular template and determine compliance.

Existing static analysis tooling has largely organized itself around this same framework boundary rather than across it. Linters such as ESLint operate through framework-specific plugins (`eslint-plugin-react`, `angular-eslint`) with independently maintained rule sets that do not share a common formal definition of what a given guideline actually means; a rule enforced for React has no guaranteed semantic counterpart enforced for Vue. Chapter 5 (Section 5.2) situates FIGM against this landscape directly, comparing it on a capability basis against Google Lighthouse, ESLint, SonarQube, `eslint-plugin-react`, and `angular-eslint`.

## 1.2 Problem Statement

Three related problems motivate this research:

1. **Fragmented, framework-coupled guideline enforcement.** No widely-adopted tool formalizes a performance or accessibility guideline once, at a level of abstraction above any single framework's syntax, and then projects that single formal definition onto each framework's own Abstract Syntax Tree (AST). Existing tools instead re-implement each guideline independently per framework, which risks semantic drift between a "React version" and a "Vue version" of what should be the identical rule.
2. **A trust gap in automated remediation.** Static analysis tools that also propose fixes commonly present a generated patch without verifying, by any automated means, that applying it actually resolves the reported violation and does not introduce a new one. A patch that merely *looks* plausible is not the same guarantee as a patch that has been re-compiled and re-scanned to confirm the original defect is gone.
3. **Unverified claims of tool effectiveness.** Detection-accuracy claims for static analysis tools are frequently reported without disclosing whether the evaluation corpus was authored independently of the tool under test — a distinction with direct bearing on how a precision/recall figure should be interpreted. This dissertation treats that distinction as a first-class methodological concern throughout (see Chapter 5, Section 5.1.1's circularity disclosure), rather than as an afterthought.

## 1.3 Research Aim

**Authoritative statement** (Research Proposal, Section 2.2; reproduced without material change in Interim Submission 02, Section 1.6): *to design, develop, and validate a comprehensive, framework-agnostic guideline model, alongside an integrated automated validation tool, to systematically improve the performance and accessibility of Single Page Applications.*

This dissertation pursues that aim through a specific technical design, described in full in Chapters 3–4: the **Framework-Independent Guideline Model (FIGM)** — a formal, four-layer meta-model (Domain → Concern → Abstract Language Primitive → Rule; see Chapter 3, Section 3.2) that expresses SPA performance and accessibility guidelines once and projects them onto real, compiler-derived Abstract Syntax Trees across multiple frontend frameworks, coupled with a remediation pipeline in which every proposed fix — deterministic or AI-assisted — is accepted only after it has been re-compiled and re-scanned to confirm the original violation is genuinely resolved. This technical design is the *means* by which the authoritative aim above is pursued; it does not replace or restate that aim, and every claim about what FIGM does traces back to it.

## 1.4 Main Research Question and Research Questions

The wording in this section is the authoritative research-question set for this dissertation, sourced verbatim from the Research Proposal (Section 2.3) and confirmed unchanged in Interim Submission 02 (Section 1.4) — Interim Submission 02, given the opportunity to revise this wording during the project's later progress stage, reproduced it without material change. This supersedes an earlier draft of this chapter that used different wording for RQ1–RQ4 (see `docs/audit/FINAL_RESEARCH_CONTRACT_RECONCILIATION_REPORT.md` and `docs/audit/STAGE_2_DISSERTATION_ALIGNMENT_REPORT.md` for the reconciliation record); the earlier draft's technical content is preserved, reframed as supplementary discussion and implementation evaluation rather than as an authoritative RQ answer, in Chapter 6.

**Main Research Question:** *How can a framework-agnostic guideline model and an automated validation tool be designed and implemented to improve the performance and accessibility of modern Single Page Applications?*

- **RQ1:** *How do different Single Page Application (SPA) render and state-management strategies influence performance metrics such as First Contentful Paint (FCP) and Time to Interactive (TTI)?*
- **RQ2:** *What framework-agnostic architectural and accessibility patterns can be identified and standardized to improve the performance and accessibility of modern SPAs in compliance with WCAG 2.2 guidelines?*
- **RQ3:** *How effectively can an automated static analysis validation tool detect architectural and accessibility violations in SPA source code before application deployment?*
- **RQ4:** *To what extent does the proposed validation tool achieve acceptable accuracy levels when compared with manual expert architectural reviews using Precision, Recall, and F1-score measurements?*

Chapter 6 (Section 6.2) reports the current, honestly-scoped answer to each. In brief, and stated here so the scope of what remains open is clear from the outset: RQ2 and RQ3 have real, evidence-backed answers from work already completed; RQ1 requires a real-browser FCP/TTI measurement experiment that has not yet been executed (the current tool reports a static scan-duration proxy, explicitly not FCP or TTI, and no result is claimed from it); and RQ4 requires comparison against real, independent expert architectural review, of which zero submissions have been collected to date (0 of a target 20 human-study participants for the *separate* developer-usability evaluation — see Section 1.7 — likewise stands at 0; neither figure should be read as evidence toward the other, since they answer different questions).

## 1.5 Research Objectives

The following four objectives, sourced from the Research Proposal (Section 2.3) and reproduced without material change in Interim Submission 02 (Sections 1.7.1–1.7.4), align one-to-one with RQ1–RQ4 above:

- **Objective 1** (→ RQ1): To analyze diverse SPA rendering and state-management strategies and evaluate their impact on performance metrics such as FCP and TTI.
- **Objective 2** (→ RQ2): To identify and define a framework-agnostic set of architectural and accessibility guidelines aligned with WCAG 2.2 standards.
- **Objective 3** (→ RQ3): To design and develop an automated static analysis validation tool capable of detecting architectural and accessibility violations in SPA projects before deployment.
- **Objective 4** (→ RQ4): To evaluate the effectiveness and accuracy of the proposed validation tool using Precision, Recall, and F1-score metrics against expert manual reviews.

## 1.6 Significance and Contributions

Independently of the four authoritative research questions above, the technical work undertaken to pursue them produced the following contributions, detailed in full in Chapter 6 (Section 6.1):

1. A four-layer meta-model formalizing 50 canonical performance and accessibility rules (`figm-spec.json`), each traceable to a specific ISO/IEC 25010 sub-characteristic or WCAG 2.2 success criterion, and each carrying a self-documented, explicit statement of its own detection scope and known limitations (`knownLimitation` field) rather than an implied claim of completeness.
2. A real-AST detection pipeline — using the TypeScript compiler API, `@vue/compiler-dom`, and `angular-html-parser` depending on the rule and framework — under which every one of the 50 canonical rules has genuine compiler-derived detection for at least one supported framework, with detection provenance (`REAL_AST` vs. `LEGACY_TEXT_HEURISTIC`) recorded and independently checkable on every diagnostic, rather than asserted as a blanket property of the tool.
3. A remediation pipeline in which a deterministic, rule-specific AST transformation is attempted first, an AI-assisted patch (via a configurable provider — Ollama, Claude, or Gemini) is attempted only when no deterministic fixer exists or applies, and — in both cases — the resulting patch is accepted as `verified` only inside a code path that has re-compiled and re-scanned it and confirmed the original violation is absent.
4. A research-integrity discipline applied throughout the empirical work: benchmark circularity (self-authored fixtures scored against self-authored ground truth) is disclosed rather than left implicit; synthetic pipeline-verification data is explicitly labeled as such and never presented as real participant or real expert data; and figures found to trace to no real computation were retracted and reported as retracted (Chapter 5, Section 5.3) rather than replaced with different unverified numbers.

These contributions are the tool's technical output; Chapter 6 discusses them as supplementary evaluation and future-work context, separately from the four authoritative RQ answers.

## 1.7 Scope and Delimitations

**Framework scope.** Per the Research Proposal (Section 4.5) and Interim Submission 02 (Section 1.10), this research is scoped to **React, Next.js, and Angular as the primary frameworks** for guideline development and evaluation. **Vue.js is additionally supported by the automated validation tool** as part of its framework detection and analysis capability (Interim Submission 02, Sections 1.10 and 2.5.2) — the guideline model itself is framework-agnostic in its formulation, but Vue was not one of the frameworks the guidelines were developed and evaluated against as primary, and no RQ1–RQ4 claim in this dissertation depends on Vue-specific results. This research does not attempt whole-project build-level analysis (e.g., a full `next build`/`ng build`), full cross-file data-flow or points-to analysis, or general-purpose security vulnerability scanning; nor does it include backend performance, network latency profiling, or cloud orchestration (Research Proposal, Section 4.5).

**Real-repository evaluation scope.** The Research Proposal (Section 4.3) and Interim Submission 02 (Section 3.4) specify a target of 20–30 public open-source SPA repositories (React, Next.js, Angular) as the real-world evaluation corpus. Chapter 5 reports the current corpus size against this target.

**Human-participant evaluation scope.** The Research Proposal (Section 4.3/5.2) and Interim Submission 02 (Sections 1.9.2, 3.4, 3.6.1, 3.6.2) document an original baseline target of 80–100 student developers at NSBM Green University for the developer-usability survey. **A later, approved research-scope decision reduced the final study target to 20 real participants** — this is the value the tool, consent form, and analysis pipeline now use throughout (`src/research/research-config.ts`'s `HUMAN_STUDY_TARGET_PARTICIPANTS`); the original 80–100 figure remains the documented historical baseline and is not erased by this reduction. See `docs/research/PARTICIPANT_TARGET_DECISION.md` for the full decision record. As of this writing, 0 of the 20 targeted participants have been collected (Chapter 6, Section 6.6).

**Accessibility scope.** WCAG 2.2 is the accessibility standard this research aligns to (Research Proposal, Section 2.3/4.5; Interim Submission 02, Section 1.4/1.6). Static analysis maps to a **statically detectable subset** of WCAG 2.2 Success Criteria; this dissertation does not claim full WCAG 2.2 conformance can be established by static analysis alone (Chapter 5).

## 1.8 Dissertation Structure

The remainder of this dissertation is organized as follows. **Chapter 2** reviews the theoretical and methodological foundations this work draws on — software quality models, design science research, compiler and program-analysis theory, and empirical software engineering research methods — and situates FIGM against the most directly comparable prior empirical work. **Chapter 3** presents the Design Science Research methodology, the four-layer meta-model, and the formal mathematical predicates underlying each rule category. **Chapter 4** details the system implementation: framework detection, the real-AST migration architecture, deterministic and AI-assisted remediation, and the sandboxed patch-verification pipeline. **Chapter 5** reports empirical validation — precision/recall/F1 against hand-labelled ground truth, a qualitative comparison against existing tools, and an honest accounting of what has and has not yet been measured for AI-remediation success rate. **Chapter 6** answers RQ1–RQ4 against the authoritative wording in Section 1.4 above, reports the developer usability evaluation status as supplementary evaluation, discusses threats to validity, and presents conclusions, contributions, and limitations.
